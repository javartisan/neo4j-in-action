# 知识融合 · 精炼学习笔记

> 目标：快速抓住实体对齐 / 本体匹配 / 冲突消解的核心，能说清「多源知识怎么合成一张可信图谱」。

---

## 一句话总览

**知识融合** = 把来自不同来源、不同模式的知识，合并成**一致、少冗余、可追溯**的一张（或一层）图谱。

| 要点 | 本质 | 解决什么问题 |
|------|------|----------------|
| 实体对齐 | 判断「是不是同一个东西」并合并 | `贵州茅台` vs `Kweichow Moutai` vs `600519.SH 发行人` |
| 本体匹配 | 判断「是不是同一个概念/关系」 | 源 A 的 `Corp` = 源 B 的 `Company` |
| 冲突消解 | 多源说法打架时如何取舍 | 董事长姓名不一致、持股比例不同 |

```text
来源1 ──┐
来源2 ──┼→ 对齐（实体/本体） → 消解冲突 → 统一图谱（带来源与置信度）
来源3 ──┘
```

与上下游：

```text
多路知识获取 → 知识融合（去重、映射、仲裁） → 干净存储 → 可靠推理/应用
```

没有融合：图谱里出现大量「假不同」节点，推理与统计都会歪。

## 1. 实体对齐（Entity Alignment / Entity Resolution）

### 核心定义

识别指向**同一现实对象**的不同实体记录，并建立等价链接或合并为一个节点。

```text
节点A: {name: "贵州茅台", source: "研报"}
节点B: {name: "Kweichow Moutai Co.,Ltd.", source: "英文公告"}
节点C: {code: "600519", source: "行情"}
       ↓ 对齐
同一公司实体（可保留多 name/别名，或 MERGE 成一个）
```

也常叫：实体解析、Record Linkage、去重（Deduplication）——场景略有差别，核心都是「同指」。

### 为什么难

| 难点 | 证券例子 |
|------|----------|
| 名称变体 | 简称/全称/曾用名/英文名 |
| 缺共同键 | 一篇只有公司名，一篇只有代码 |
| 同名异实 | 不同主体重名（需靠代码、统一社会信用代码等消歧） |
| 粒度不同 | 「茅台集团」vs「贵州茅台酒股份有限公司」 |

### 对齐信号（由强到弱）

| 信号 | 强度 | 例子 |
|------|------|------|
| 全局唯一 ID | 极强 | 股票代码、统一社会信用代码、LEI |
| 多属性一致 | 强 | 名 + 注册地 + 代码 |
| 字符串相似 | 中 | 编辑距离、拼音、别名词典 |
| 结构相似 | 中 | 共同邻居、同一行业与竞品集合 |
| 向量近邻 | 中 | 名称/描述 Embedding |
| 仅简称撞车 | 弱 | 必须再找硬证据 |

### 工程两步

1. **判定**：`(e1, e2)` 是否同一实体（规则 / 分类模型 / 人工）  
2. **合并策略**：
   - **软对齐**：保留两节点，加 `SAME_AS` / `owl:sameAs` 边  
   - **硬合并**：`MERGE` 成一个节点，属性按规则汇总，边迁过去  

```cypher
// 软对齐示意
MATCH (a:Company {name:$n1}), (b:Company {name:$n2})
MERGE (a)-[:SAME_AS {method:'code', conf:1.0}]->(b)
```

### 本项目相关现状

当前用 `name + entityType` 做 `MERGE`，**同名同类型会并成一个**——这是最简对齐。

尚未覆盖：中英名、曾用名、跨文档「茅台」与「贵州茅台酒股份有限公司」等。升级时可加**别名词表 + 代码桥接**。

### 速记

- 实体对齐回答：**「多个提及是不是同一个现实对象」**
- 口诀：**先硬键（代码），再名字，最后向量；合并前保留来源**

## 2. 本体匹配（Ontology Matching / Schema Matching）

### 核心定义

在不同本体或数据模式之间，建立**概念/属性/关系的对应**，使两边的数据能互相翻译。

```text
源系统A：Corp  --listedCode-->  Ticker
源系统B：Company --LISTED_AS--> Stock
              ↓ 本体匹配
Corp ≡ Company
Ticker ≡ Stock
listedCode ≡ LISTED_AS
```

实体对齐解决「实例层同指」；本体匹配解决「模式层同义」。

### 匹配什么

| 层 | 匹配对象 | 例子 |
|----|----------|------|
| 类 | `Industry` ↔ `Sector` | 是否同一类概念 |
| 关系 | `控股` ↔ `CONTROLS` | 是否同一谓词（含方向） |
| 属性 | `证券代码` ↔ `code` | 是否同一数据字段 |
| 约束 | 基数、互斥是否兼容 | 匹配后能否一起推理 |

### 常用方法（由易到难）

| 方法 | 做法 |
|------|------|
| 词典/同义词表 | 人工维护「Corp=Company」 |
| 名称相似 | 字符串/翻译后相似度 |
| 结构相似 | 类的属性集合、在层次中的位置相近 |
| 实例反馈 | 两类实例大量对齐 ⇒ 类也可能对齐 |
| 嵌入/LLM 辅助 | 用描述文本向量或提示做候选，人工确认 |

### 最小证券例子

| 外部模式 | 本仓库本体 | 匹配 |
|----------|------------|------|
| `Org` | `Company` | 类等价（若仅指法人） |
| `Executive` | `Person` + 关系 `HAS_EXECUTIVE` | 类 + 关系共同表达 |
| `belongs_industry` | `BELONGS_TO` | 关系等价 |
| `sec_code` | `Stock.name` / `code` | 属性映射 |

匹配结果通常落成一张 **Mapping 表**（或 OWL `equivalentClass` / `equivalentProperty`），ETL 时按表转换再入库。

### 和「知识表示」的关系

- 两边都先有（或不完善的）Ontology/Schema  
- 匹配质量上限受两边建模清晰度限制  
- 匹配后才谈得上跨源推理与统一查询  

### 速记

- 本体匹配回答：**「你的词和我的词是不是一个意思」**
- 口诀：**先对齐类与关系名，再导数据；映射表要版本化**

## 3. 冲突消解（Conflict Resolution）

### 核心定义

当多源对同一对象给出**矛盾断言**时，按策略选出可信结论，或保留多值并标注争议。

```text
源1：贵州茅台 董事长 = 丁雄军   (研报2023)
源2：贵州茅台 董事长 = 某人X     (旧闻2018)
         ↓ 冲突消解
采纳：丁雄军；旧值归档为历史；记录证据与时间
```

冲突不只存在于属性值，也包括：

- 关系有无（A 是否控股 B）  
- 类型互斥（既是 Person 又是 Company——本体层也会报）  
- 数值不一致（持股 10% vs 12%）  

### 常见消解策略

| 策略 | 做法 | 适用 |
|------|------|------|
| 来源优先级 | 交易所公告 > 研报 > 自媒体 | 权威等级清晰时 |
| 时间最新 | 取最新时间戳 | 易变属性（高管、持股） |
| 多数投票 | 多源一致则信 | 冗余采集 |
| 置信度加权 | 按抽取模型分数加权 | NER/RE 流水线 |
| 数值融合 | 平均/中位数/区间 | 估算类指标（慎用） |
| 人工裁决 | 工单审核 | 高风险结论 |
| 保留冲突 | 多值并存 + `contested` 标记 | 暂不能判、需展示争议 |

### 工程上建议始终记录的元数据

```text
value / 关系
  + source（哪篇文档、哪个系统）
  + time（事实时间或采集时间）
  + confidence
  + method（抽取规则 / 人工）
```

没有元数据，冲突消解只能拍脑袋。

### 与推理的关系

- **本体推理**可发现逻辑冲突（互斥类）  
- **冲突消解**处理多源事实冲突（谁说了算）  
- 流程常是：对齐同一实体 → 汇总其多源断言 → 消解 → 再跑推理校验  

### 本项目可演进点

当前多次上传会 `MERGE` 同名实体并 `SET` 属性，**后写可能覆盖先写**，且缺少来源级冲突记录。增强方向：

- `MENTIONS` 已保留文档溯源（起点）  
- 属性改为「来源事实表」或关系属性上挂 `source/time/conf`  
- 对外查询时按优先级选出「当前真值」

### 速记

- 冲突消解回答：**「多源打架时听谁的、怎么留痕迹」**
- 口诀：**权威 > 时间 > 置信度；关键字段可人工；永远可追溯**

## 融合流水线（串起来）

```text
1. 本体匹配     ：把各源 Schema 映射到统一本体（本仓库 types.ts）
2. 数据转换     ：字段/关系改名、类型归一
3. 实体对齐     ：硬键（股票代码）→ 别名 → 相似度候选 → 审核
4. 图合并       ：SAME_AS 或硬 MERGE，边迁移
5. 冲突消解     ：按策略生成「当前视图」
6. 质检/推理    ：互斥、必填、规则校验
7. 发布         ：应用只读「已融合层」，原始层可另存
```

| 层级 | 内容 |
|------|------|
| 原始层 | 各源原样，尽量不改 |
| 对齐层 | `SAME_AS`、Mapping |
| 融合层 | 对外服务的统一实体与真值 |

5. 为什么融合要保留来源与时间？

**参考答案要点**：  
①同指、同义模式、矛盾仲裁；获取产事实，融合成一张可信网  
②唯一 ID；SAME_AS vs 并成一点  
③概念/关系；Corp≡Company 等  
④权威源、最新时间、投票/人工  
⑤否则无法审计、无法按时间回滚真值

## 建议学习顺序

1. 承认多源必然有「同名异实 / 异名同实 / 打架」  
2. 先做 **ID 桥接**（股票代码）与 **别名词表**  
3. 固定统一本体，再写 **Schema Mapping**  
4. 设计属性级 **source/time/conf**，再谈消解策略  
5. 需要大规模自动对齐时，再上相似度/Embedding，并保留人工审核入口
