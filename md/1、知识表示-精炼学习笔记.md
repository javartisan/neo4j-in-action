# 知识表示 · 精炼学习笔记

> 目标：快速抓住 Ontology / RDF·OWL / Embedding 的核心，能说清「是什么、为什么、怎么用」。

---

## 一句话总览

**知识表示** = 把现实世界的概念与关系，变成计算机可存储、可查询、可推理的形式。


| 路线        | 本质            | 强项          |
| --------- | ------------- | ----------- |
| Ontology  | 人可读的领域模型约定    | 语义清晰、可共享    |
| RDF/OWL   | 形式化三元组 + 本体语言 | 互操作、逻辑推理    |
| Embedding | 向量空间数值表示      | 相似度、补全、机器学习 |


三者关系：**Ontology 定语义 → RDF/OWL 落形式 → Embedding 做计算增强**（可并存，非互斥）。

## 1. Ontology（本体）

### 核心定义

本体是对某个领域中**共享概念体系**的形式化规范说明：有哪些类、属性、关系，以及它们之间的约束。

### 必须记住的 4 个构件

1. **类（Class / Concept）**：事物类别，如 `Company`、`Stock`
2. **个体（Individual）**：类的实例，如「贵州茅台」
3. **属性（Property）**
  - 对象属性：实体→实体（`BELONGS_TO`）
  - 数据属性：实体→字面量（`stockCode = "600519"`）
4. **公理/约束（Axiom）**：如子类、互斥、基数、定义域/值域

### 和「Schema / 数据模型」差在哪


|     | Schema（库表/图模型） | Ontology  |
| --- | -------------- | --------- |
| 目的  | 支撑存储与查询        | 支撑共享语义与推理 |
| 重点  | 字段、类型、索引       | 概念层次、逻辑约束 |
| 跨系统 | 常难对齐           | 强调可复用、可对齐 |


> 实务口诀：**先本体后落库**——证券 KG 里先定「公司/股票/行业/关系」，再映射到 Neo4j 标签与边类型。

### 最小例子（证券）

```text
类：Company ⊇ ListedCompany
关系：ListedCompany —LISTED_AS→ Stock
约束：一只 Stock 至少对应一家 ListedCompany（业务规则可写成公理）
```

这三行合起来是一段完整的本体片段（**类层次 + 关系 + 约束**），不是随便画两个框一条线。

#### ① `Company ⊇ ListedCompany`

读作：**Company 包含 ListedCompany**，即 **ListedCompany 是 Company 的子类**。

- `⊇`：集合上的「超集」符号 → 等价说法是 `ListedCompany ⊆ Company`
- 推论：若某实体是「上市公司」，则它一定也是「公司」
- 类比：动物 ⊇ 狗 → 狗是动物的一种

#### ② `ListedCompany —LISTED_AS→ Stock`

读作：**上市公司 通过关系 LISTED_AS 指向 股票**。

- 左边：关系起点类型（定义域）= `ListedCompany`
- 中间：关系名 ≈「上市为 / 对应证券」
- 右边：关系终点类型（值域）= `Stock`

具体事实示例：

```text
贵州茅台(ListedCompany) —LISTED_AS→ 600519(Stock)
```

#### ③ 「一只 Stock 至少对应一家 ListedCompany」

这是对关系的**基数约束（公理）**：

> 每个 `Stock` 至少有一条「从某家 ListedCompany 出发、指向它」的 `LISTED_AS` 边。

- 不允许「孤儿股票代码」（有代码但图谱里挂不上公司）
- 「至少一家」= 基数下界 ≥ 1（现实里多为 1 对 1，这里只强制不能为零）

**合在一起的业务含义**：先有「公司」大类，其中一部分是「上市公司」；上市公司可「上市为」某只股票；每只股票在图里都必须能挂到至少一家上市公司。

### 速记

- 本体回答：**「这个领域里，词是什么意思、能不能连、有什么限制」**
- 不做本体 → 多源数据难融合，关系命名混乱，推理无从谈起

## 2. RDF / OWL

### RDF：资源描述框架

**一切皆三元组（Triple）**：

```text
Subject  —Predicate→  Object
主体     —谓词→       客体
贵州茅台 —属于→       白酒行业
```

- 资源用 **URI/IRI** 标识（全球唯一）
- 客体可以是资源，也可以是字面量（字符串、数字、日期）
- 多条三元组连成 **RDF 图**

**为什么重要**：同一事实用标准结构表达，不同系统能交换、能合并。

### RDFS：轻量词汇层

**RDFS** = **RDF Schema**（RDF 模式 / RDF 词汇描述语言）。

- **RDF**：Resource Description Framework（资源描述框架）
- **Schema**：模式（在 RDF 之上定义类、属性、定义域/值域等轻量语义词）

在 RDF 之上增加常用语义词，例如：

- `rdfs:subClassOf`：子类
- `rdfs:domain` / `rdfs:range`：属性定义域/值域
- `rdf:type`：实例属于某类

→ 已能做**有限推理**（如：已知是子类实例 ⇒ 也是父类实例）。

### OWL：更强的本体语言

OWL（**Web Ontology Language**，网络本体语言）在 RDFS 之上加强逻辑表达，常见能力：


| 能力    | 例子                                         |
| ----- | ------------------------------------------ |
| 等价/互斥 | `Company ≡ Corporation`；`Person ⊥ Company` |
| 属性特征  | 对称、传递、函数性（最多一个值）                           |
| 基数约束  | 一家公司恰好 1 个法人代表（业务上可建模）                     |
| 复杂类定义 | 「有股票代码的公司 = 上市公司」                          |


**推理器**可据此推出未显式写入的事实（本体推理）。

### OWL 最小工程示例（证券）

下面用 **Turtle** 语法写一份「能跑推理」的迷你本体（完整文件见 `md/examples/securities-mini.ttl`）。

**只表达 3 条规则 + 2 条事实：**

1. `ListedCompany` 是 `Company` 的子类
2. `Person` 与 `Company` 互斥（一个人不能同时又是一家公司）
3. `listedAs`：从上市公司指向股票，且**函数性**（一家公司最多对应 1 只主股票，简化示例）
4. 事实：茅台是 `ListedCompany`，并 `listedAs` 600519

```turtle
@prefix :    <http://example.org/sec#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs:<http://www.w3.org/2000/01/rdf-schema#> .

:Company        a owl:Class .
:ListedCompany  a owl:Class ; rdfs:subClassOf :Company .
:Stock          a owl:Class .
:Person         a owl:Class ;
                owl:disjointWith :Company .   # 互斥

:listedAs a owl:ObjectProperty , owl:FunctionalProperty ;
          rdfs:domain :ListedCompany ;
          rdfs:range  :Stock .

:Moutai a :ListedCompany ;
        :listedAs :S600519 .
:S600519 a :Stock .
```

**工程里怎么用（三步就够）：**


| 步骤    | 做什么              | 常用工具                                     |
| ----- | ---------------- | ---------------------------------------- |
| 1. 建模 | 用编辑器写/画上述公理与实例   | [Protégé](https://protege.stanford.edu/) |
| 2. 推理 | 启动推理器，自动补全隐含事实   | HermiT / Pellet（Protégé 内置可选）            |
| 3. 消费 | 查询推理后的图，或导出给业务系统 | SPARQL / 再导入图库                           |


**推理器会多「算」出什么（你没手写的）：**

```text
:Moutai rdf:type :Company
# 因为 ListedCompany ⊑ Company，实例继承父类
```

若有人误写 `:Moutai a :Person`，推理器会报**不一致**（与 `disjointWith Company` 冲突）——这就是 OWL 在工程上的价值：**校验 + 自动补全**，而不只是存数据。

**和本仓库 Neo4j 的对照（务实结论）：**


| OWL 做法                              | 本项目常见做法                                     |
| ----------------------------------- | ------------------------------------------- |
| `.ttl` + 推理器推 `Moutai` 也是 `Company` | 入库时直接打上 `Company`/`ListedCompany` 标签，或应用层约定 |
| `FunctionalProperty` 由推理器/校验器保证     | 用约束、唯一索引或写入前校验                              |
| 适合语义互操作、强一致性校验                      | 适合业务查询、可视化、高吞吐                              |


> 多数业务 KG：**Neo4j 存运行数据，OWL/本体文档（或等价 Schema）定语义契约**；只有强推理需求才上完整 OWL 推理栈。

### OWL 与 RDFS 的关系

**OWL 建立在 RDF/RDFS 之上，是能力更强的一层；不是互相替代。**

```text
OWL   ← 更强的本体语言（逻辑更丰富，可做更复杂推理）
 ↑
RDFS  ← 轻量「词汇/模式」层（类、属性、定义域/值域、子类等）
 ↑
RDF   ← 底层数据模型（三元组）
```


|      | RDFS         | OWL                            |
| ---- | ------------ | ------------------------------ |
| 定位   | 轻量 Schema    | 完整本体语言                         |
| 典型能力 | 类层次、属性定义域/值域 | 等价/互斥、传递/对称、基数、复杂类定义…          |
| 推理   | 有限（继承类推等）    | 更强（依赖所选 OWL 子集与推理器）            |
| 复杂度  | 低，好上手        | 高，需注意 OWL Lite / DL / Full 等档位 |


一句话：

- **RDFS**：先能描述「有哪些类、属性怎么连」
- **OWL**：再能精确说「类能否等同/互斥、属性有无传递性、某类必须满足什么约束」

实务：小项目用 RDFS 思想（甚至直接落到 Neo4j Schema）往往够用；要严格语义互操作或自动推理，再上 OWL。

### RDF 栈速记

```text
OWL（强逻辑） ⊃ RDFS（轻词汇） ⊃ RDF（三元组） ⊃ IRI + 字面量
```

（表达能力上大致如此；OWL 语句本身也常以 RDF 三元组形式序列化。）

### 和 Neo4j 属性图怎么对照


| RDF 世界     | Neo4j 属性图（本项目）          |
| ---------- | ----------------------- |
| 资源（IRI）    | 节点 + `id`/`name`        |
| `rdf:type` | 标签 Label / `entityType` |
| 谓词         | 关系类型 RelType            |
| 字面量        | 节点/关系属性                 |


> 属性图更工程友好；RDF/OWL 更偏语义网与严格推理。证券业务系统多数用 Neo4j，但**本体思想仍要保留**。

### 速记

- RDF：**统一的「主-谓-宾」信封**
- RDFS：**信封上的轻量标签（类层次、定义域/值域）**
- OWL：**在信封上写清更强逻辑规则，让机器会推**

## 3. Embedding（知识表示学习）

### 核心定义

把实体、关系映射到低维稠密向量，使**图结构与语义**体现在向量空间的几何关系中。

```text
实体 e → 向量 e⃗ ∈ R^d
关系 r → 向量/矩阵 参数
目标：真实三元组 (h,r,t) 得分高，假三元组得分低
```

### 为什么需要它

符号表示（Ontology/RDF）擅长精确与可解释；但面对：

- 大规模稀疏图
- 缺失链接要预测
- 语义相似要计算

→ Embedding 更擅长做**补全、检索、推荐、聚类**。

### 经典范式（只记直觉）


| 模型族              | 直觉                           |
| ---------------- | ---------------------------- |
| **TransE** 等平移模型 | `h⃗ + r⃗ ≈ t⃗`（头实体加关系 ≈ 尾实体） |
| **双线性/语义匹配**     | 用矩阵/张量给 `(h,r,t)` 打分         |
| **图神经网络 GNN**    | 邻居消息传递，学节点表示                 |


### 能做什么

1. **链接预测**：可能还缺哪条边？
2. **实体相似度**：向量近 ⇒ 语义/结构近
3. **与 NLP 对齐**：文本向量 ↔ 实体向量（多模态 KG）

### 和符号表示的关系

```text
符号层（Ontology/RDF/图库）  ←精确、可审计、可规则推理
        ↕ 可互相增强
向量层（Embedding）         ←模糊匹配、补全、端到端学习
```

生产上常见组合：**Neo4j 存真源事实 + Embedding 做召回/预测 + 规则做校验**。

### 速记

- Embedding 回答：**「谁和谁像、缺的边可能是什么」**
- 不是替换本体，而是给知识图谱加上**可计算的几何层**

## 建议学习顺序

1. 先画本领域 **Ontology 草图**（类 + 关系）
2. 用 **三元组思维**检查每条业务事实能否写成 `(s,p,o)`
3. 落到 **Neo4j**（本仓库已在做）
4. 有规模与补全需求时再学 **Embedding**
